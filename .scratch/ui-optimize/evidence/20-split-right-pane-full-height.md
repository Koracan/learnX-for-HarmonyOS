## 1. 实现路线与理由（ticket 要求先选一条并写理由）

选了**路线一**：内容区（壳层 `Tabs`）在分栏态拿满整屏高，**由五个页面各自在自己的主栏底部预留 barH**。
不选路线二（把底栏下放到各页 `masterPane` 内部）的理由：

1. 底栏是**壳层的东西**（它要 `activeIndex` / `switchTo` 五个 tab 的控制器）。下放意味着 5 份底栏 UI + 一条回调链，
   而 ticket 的 C.2 恰好要求 barH 与预留量只有**一处**来源 —— 5 份拷贝是最容易分叉的形状。
2. 更硬的一条：单栏态必须与改前**逐字节兼容**（B.1）。路线二会把底栏节点搬进页面子树（dump 的树路径整段改变），
   而路线一在单栏态**一行版式都没动**（新加的两个修饰符取值为 0：`margin.top = 0`、`padding.bottom = 0`）。
3. 参考实现本来就更接近路线一（底栏属左栏那一支，`SplitView.tsx`），本工程不必再为它改结构。

路线一的具体落法（**没有新增任何尺寸常量**）：

- `features/shell/SplitView.ets` 新增纯函数 `splitHeightBudget(splitActive, masterHidden, 屏高, barH)` 与 `masterPaneBottomReserve(theme, …)`、
  `bottomBarHeight(theme)`：barH 的算法与「主栏底部预留多少」都只在这里；
- 壳层 `ShellTabs.tabBar()` 在分栏态给底栏 `margin.top = −barH` —— 负 margin 只让它**不占**流内高度，
  它的盒子仍落在 `[屏高 − barH, 屏高]`，位置与单栏一致（实测 `Row [0,1752,786,1864]` 与改前逐值相同）；
- 五个页面（notices / assignments / files / courses / settings）各自给主栏 Column 加 `padding({ bottom: masterPaneBottomReserve(...) })`，
  分栏态 = barH、单栏态 = 0。

## 6. 未做到 / 存疑（如实）

### 6.1 A.1 的「= 屏幕下边界（1920px）」：应用排不到 1920

ticket 里写的 1920 是**物理屏**高。实测本机应用**渲染区**是 `y∈[86,1864]`：
窗口根 `root [0,86,2880,1920]`（1834 高），但应用自己的壳 Column 只有 1778（下边界 1864），
下面的 56px 是系统手势条安全区（帧里可见那条居中的横线）。
改后右栏下边界 = **1864 = 应用渲染区下边界 = 底栏下边界**，也就是应用这一层能排到的最后一像素；
要让某个组件落到 y=1920 得先扩安全区（`expandSafeArea`），那会同时把底栏也推下去、直接违反 A.2，故不在本 ticket 范围内。
旁证：ticket 04 已验收的分栏帧里底栏命中区也是 `[0,1754,…,1864]` —— 本工程的几何基线一直以 1864 为下边界。

### 6.2 A.1 的「多出一个 ListItem」：本账号数据排不出这么长的右栏列表

本账号（真实站点数据）右栏所有列表都**短于视口**，改前根本没有「最后一条被截」的列表，
所以这条的**字面形式**（多一个 ListItem / 某行原先被截、现在完整）拿不到：

- 学期列表（设置 → 学期切换）：9 条 × 112px = 1008px，视口改前 1554 / 改后 1666 ⇒ 不溢出；
- 课程详情的文件列表：4 条 × 120px = 480px，视口 1398 / 1510 ⇒ 不溢出；
- 公告/课程主栏列表各 2 条。

替代证据（同一件事的等价值，已在上表与两帧里给出）：**同一份文档、同一滚动位，改后多显示 112px**
（文档容器 1390 → 1502；尾部那张图可见高 646 → 758），帧上表现为原先被切掉半截的那一行现在整行可读。
抓不到就说抓不到 —— 不拿「看起来好了」当这条的证据。

### 6.3 一处未归因、但无可见后果的容器盒异常

改后 `Tabs`/`Swiper` 的盒报 `[0,86,2880,1920]`（1834 高）：比它们的父 Column（1778）高 56px、
也比它们自己的内容 `TabContent [0,86,2880,1864]`（1778）高 56px。
**内容盒是对的**（`TabContent` / 页面 `Row` / 两栏都在 1864 收住），两帧里也没有任何可见异常；
它超出的是系统手势条那一条安全区，那里本来就不画应用内容。
机制未查明（怀疑与 `margin` 负值在 Tabs 尺寸分配里的处理有关），**如实记录**：
若后续有 agent 要清掉它，可用「零高 wrapper + translate」替代负 margin，但那条路依赖子节点溢出渲染，未实测。
