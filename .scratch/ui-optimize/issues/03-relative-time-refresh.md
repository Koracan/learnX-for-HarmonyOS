# 03: 页头相对时间不再冻结

**What to build:** 页头的相对更新时间在每次页面被显示时重新计算，而不是在页面构造那一刻算一次就冻住。
用户从别的 tab 切回来、或从后台回到前台，看到的时间必须是当下的；四个档位（刚刚 / N 分钟 / N 小时 / N 天）的措辞不变。

**Blocked by:** None（可立即开始）

**Status:** verified（合并 `a312310`：契约一处实现 + 三帧设备证据，其中一对严格无抓取）

- [x] 页面重新显示时，页头时间文本按当前时间重算
- [x] 档位边界（59 秒 / 60 秒 / 59 分钟 / 60 分钟 / 23 小时 / 24 小时）仍由既有单测钉住且全绿
- [x] 页面重新显示这件事有一个可命名的动作，四个列表页共用同一个模式（不各写一套）
- [x] 证据：同一台设备上「进页面 → 等 ≥2 分钟 → 切走再切回」两帧截图/布局文本，时间文本确实变了

## Comments

### 2026-09-13 · 统筹者派单前的约束与提示（不是验收条款，是省你一轮返工的现场情报）

**现状（我已读过代码，四个页面同构）**：页头那一行是各页自己的方法，形如
`private updatedText(): string { return updatedTimeText(this.store.fetchedAtMillis, Date.now()); }`
（`NoticesPage.ets:156`、`AssignmentsPage.ets:236`、`CoursesPage.ets:221`、`FilesPage.ets:202`），
在 `build()` 里被调用一次。`updatedTimeText` 本身是**纯函数且有单测**（`ui/components/UpdatedTime.ets`）——
**把它改掉不是本 ticket 的做法**：它没错，错的是"只在页面构建那一刻算了一次"。

**三条硬约束**：
1. **一个可命名的动作，四处订阅同一个契约**：不要四个页面各写一个定时器 / 各写一套 `aboutToAppear` 重算。
   形状建议（名字可改、契约不可散）：`features/shell/PageShown.ets` 导出 `PAGE_SHOWN_TICK_KEY` 与 `markPageShown()`，
   四个列表页各自声明同一个 `@StorageProp(PAGE_SHOWN_TICK_KEY)`；动作只在这个文件里实现一次。
2. **两个触发源必须汇进同一个动作**：切 tab（`ShellTabs.ets:364` 的 `.onChange`）与回到前台（`EntryAbility.ets:185` 的 `onForeground`，目前只有一行日志）。
3. **事件驱动，不是心跳**：不要为了这一行加 1 秒定时器 —— 工单要求的是"页面被显示时重算"，不是"持续刷新"。

**两个坑（我替你先踩了）**：
- **`onPageShow` 在这四个页面上不存在**：它是 `@Entry` 页面级生命周期，而这四个是 shell 里的子组件（`TabContent(){ NoticesPage() }`）。所以必须从上往下发信号，别在页面内部找生命周期回调。
- **`ShellTabs` 自己重绘 ≠ 子页面重绘**：`.onChange` 里给 `this.activeIndex` 赋值只会重绘 `ShellTabs`，`TabContent` 的子组件实例是持久的、`build()` 不会重跑。这就是现在时间会冻住的原因 —— 也让"顺手在 onChange 里改个 state 就完事"这种做法**看起来像修好了、实际没修**。

**验收口径提醒**：工单只要求**既有**四档边界单测仍然全绿（不是新增边界测试）；新增的可测部分请只钉你能钉的（例如动作把计数推进了、纯函数在给定的 (fetchedAt, now) 下给出预期档位），
**不要**在单测里断言"UI 重绘了" —— 那只有设备能给答案。设备证据按工单写：同一台设备、同一状态、间隔 ≥2 分钟、切走再切回，两帧的**布局文本**里那一行必须不同（截图 + layout dump 各留一份）。
**不许改设备时钟**（会牵动别人的登录会话与 TLS 校验）—— 就等真实的两分钟。

### 2026-09-13 · 统筹者验收：**verified**（合并 `a312310`）

**我独立复核过的东西**：
- **"只有一处实现"我用 grep 自己数过**：`AppStorage.setOrCreate(PAGE_SHOWN_AT_KEY, …)` 在 `entry/src/main` 全树**恰好 1 处**（`PageShown.ets:59`＝`markPageShown`）；`@StorageProp(PAGE_SHOWN_AT_KEY)` **恰好 4 处**（四个列表页各 1）；`pageHeaderUpdatedText` 声明 1 处、四个页面各一行调用；`updatedTimeText` 现在只被 `PageShown.ets` import。契约形状（一个键 + 一个动作 + 四处订阅）与工单要求相符。
- **`UpdatedTime.ets` 与 `UpdatedTime.test.ets` 不在 diff 里**（纯函数与四档边界一个字未改）；`Tests run: 426 / Failure: 0 / Error: 0`（`test_result.txt` 时间戳 `2026/9/13 13:59:47`；改动前基线 423 ⇒ +3 条 `PageShown`）。
- **三帧的页头文本我直接从 layout dump 里读了出来**（不依赖截图转述）：`frame1 = "刚刚更新"`、`frame2 = "3 分钟前更新"`、`frame3 = "6 分钟前更新"`。
- **判别性我认**：帧 2 → 帧 3（HOME 进后台 → `aa start` 回前台）之间的**全部应用日志**只有几条生命周行 + 1 条 `page shown: source=ability-foreground` —— 没有任何 `data.*` / `network request #N` / `refresh done`，所以那一帧的变化不可能来自"抓取把 `fetchedAt` 推新了"。帧 1 → 帧 2 更硬：切到作业页**确实**触发了一次抓取，但那是作业页自己的 `CourseListStore`；**算术可证伪** —— 若公告 store 在切走那刻被抓，那一帧该读 `1 分钟前`，切回那刻被抓该读 `刚刚更新`，实测 `3`，只与冷启动那次 `fetchedAt` 相符。
- **命名偏离我认**：工单 Comments 建议 `PAGE_SHOWN_TICK_KEY`，实现用了 `PAGE_SHOWN_AT_KEY`（值是**时刻**而非计数）。名字不在验收条款里，且用时刻做基准才能让这一行在两次显示之间稳定 —— 契约形状未变，接受。

**关于它提的那个设计问题（基准取"显示时刻"还是"求值那一刻"）：我裁定维持现状**，理由三条：
1. 这一行回答的语义就是"**我进这个页面时**数据是多久以前更新的"，基准＝显示时刻是自洽的，而且写进了文件头。
2. 改成"任何重绘都取当下"会让那个订阅变量在产出文本的表达式里**不再被使用** —— 而 ArkUI 是按"更新函数执行时读了哪些状态变量"登记依赖的（实现方把这一点也写进了注释）。那样触发机制就建立在一个**未经验证的框架行为**上，必须重做一次设备验证；为一个人眼几乎碰不到的边角，代价不成比例。
3. 两者的可见差别只出现在"停在页面上很久、又因为别的原因（切筛选片 / 主题 / 语言）重绘"这一种情形。
⇒ 作为**候选**记在这里：*若账号所有者要求"任何重绘都取当下"，改法是让基准成为 `max(显示时刻, 当下)`（既保证订阅被真实使用、又让任何重绘都取当下），但那要重做一次设备验证*。

**如实记录的限制（不因此降级）**：设备帧只覆盖 JUST_NOW 与 MINUTES 两档（HOURS / DAYS 需要 1 小时以上的旧快照，本轮没出现，那两档只有既有单测的键映射兜着）；四个页面共用同一处实现（grep 可复核）但只对**公告**页取了设备帧；"回前台"只验了 HOME + `aa start` 一条路径；帧 2/3 的"只变一行"是**文本节点**层面的 diff（bounds 也相同），没做像素级比较。

**它主动做的两处"两边留话"我认可**：`docs/accepted-deviations.md` 第 24 条加了带日期的追记（那一条原文写"不每秒重算（只在进入页面 / 刷新后取一次）"，本次改的正是"进入页面"落不落地 —— 追记说明的是"让实现对得上原措辞"，不是推翻它）；`.scratch/ui-optimize/evidence/README.md` 里给 ticket 01 的页头 dump 论断加了追记（那一行仍在，但取值不再冻结）。这正是 `concurrency.md` 要求的"改掉别人证据依赖的前提时两边都要留话"。
