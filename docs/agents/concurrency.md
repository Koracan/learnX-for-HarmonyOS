# 并发与协作（多 agent 同仓时）

> 由 `AGENTS.md` 指向：**要与别的 agent 并行、要拿构建或设备、要开 worktree、或你的改动可能影响别人已验收的证据时读这里。**

## 两把锁

**构建产物与设备都是单例资源**，同一时刻只允许一个 agent 占用。别只按"设备"分——实际上是两把：

1. **构建锁** —— 任何 `hvigorw`（**含 `test`**）与 `devecocli build` 都会写 `entry/build` 与 `.hvigor` 缓存。
   **同一时刻只允许一个构建进程**：两个并发构建会互相污染产物，并给出不可信的编译/测试结果。
2. **设备锁** —— `devecocli install/run`、`devecocli ui`（截图 / layout / 点击）、`devecocli log`、任何 `hdc` 命令。
   同一时刻只允许一个 agent 操作一台设备。

`devecocli run` 同时占两把锁（既构建又安装）。**两把锁相互独立**：改代码与读文件不需要任何锁，
所以"改代码"和"占设备取证"可以真并行——这才是让多 agent 不排长队的办法。

**要独占时向统筹者申请窗口**，不要在共享资源上自行重试或抢占；拿到窗口的 agent 收尾时明确回报**"窗口关闭"**。

已实测的代价：两个 agent 同时跑构建会互相覆盖 `entry/build/default/outputs/default/entry-default-signed.hap`，
后者的产物会让前者**已装的 app 与源码对不上**；两个 agent 操作同一台模拟器会让 install / 点击 / 截图互相踩踏。

## 多 worktree 并行

判据是**有独立设备**。worktree 只隔离文件系统，不给你第二台模拟器；没有独立设备就不要开——那只是把文件冲突换成设备冲突。
两台设备在线时，可以给每条线配一棵 worktree + 一台设备。

- **它解决的**：每棵树有各自的 `entry/build` ⇒ 构建产物不再互相覆盖。
- **它不解决的**：两把锁仍各只有一把；跨树并行的是"改代码 + 各自构建 + 各自取证"。
- **实测**（两棵 `--detach` worktree 同时 `assembleHap --no-incremental`）：两棵各约 45s、都 BUILD SUCCESSFUL，
  **各自起自己的 hvigor 守护进程**（各约 2s 就绪），没有出现 `no-daemon mode`、也没有 `Another build is already running`；主树产物时间戳未被动。
  ⇒ **"构建成本翻倍"要收窄**：真正重复的只是 ohpm 安装与缓存构建的一次性成本（本仓库 `oh_modules` 仅 0.3 MB），
  **不是每次构建的墙钟时间**——并发与单棵基线相比几乎没有惩罚。
- **签名材料不用复制**：`build-profile.json5` 的 `signingConfigs` 指向**用户级** `~/.ohos/config/` 下的绝对路径，新树天然能读到。
## 开工前先自证「我在哪棵树」（2026-09-13 实测事故）

一名 agent 把**整个工期的改动、构建与取证**都做在了**另一名 agent 的 worktree** 里：两边的 `entry/build` 与工作区互相污染，
被污染方的产物无法证明「装的是哪一笔」，误置方那批帧/日志只能作废重做（时间与设备机时都白烧）。当时两边都**没有**违反设备锁——坏的只是树。

- 每个 agent **开工前与每次构建/取证前**用 `git rev-parse --show-toplevel` 确认自己在派单指定的那棵树。
- **派单里没有真路径时不许自己挑树。** 本次事故的根因在统筹者一侧：派单模板的占位符替换把整段路径吃掉了，agent 收到的原文里只有 `WT` / `BRANCH` / `DEV` / `TICKET` 这样的占位符；
  其中一名 agent 没有停下询问，而是自己选了一棵树，正好选到别人的树。⇒ 派单里出现**占位符、空路径、或与 ticket 文件不一致**时，**停下回报统筹者**，不要以任何一方"为准"自行推进。
- 统筹者发派单前**自查一遍**：路径必须是可执行的字面量（发完用会话缓存或让 agent 回贴一次 `git rev-parse --show-toplevel` 验证）。
- `git status` 或 `git log` 里出现**不属于你**的东西 ⇒ **立刻停下回报统筹者**：不要回退、不要提交、不要"顺手改成自己的"。
- 统筹者处置串树的顺序：① 把误置的**未提交改动字节级搬到它该在的树**（另存一份 patch 兜底）；② 把误置方的**证据与日志移到树外的隔离目录**（`learnOH-wt/_quarantine-*`，**不要直接删**）；③ 复原被污染的那棵树，并在**两个** ticket 里各写一句「变了什么、原证据作废到哪一步」。

- **收尾要清两样**：① `git worktree remove --force <path>`；② **先杀掉该树的 hvigor 守护进程**，否则目录会因文件占用删不掉
  （现象 `failed to delete …: Permission denied` / `the file is being used by another process`）。
  定位：查 `node.exe` 进程的命令行里是否含该树的路径片段——**别按时间盲杀，那样会误杀主树的守护进程**。

## 工作区是共享的

**任何"半成品"都会冻住别人的构建。** 实测过两次：一个 ticket 留下 21 个编译错误挡住另一个；
另一个给接口加了必填字段却没同步它的测试，对方 `COMPILE RESULT:FAIL {ERROR:2}`、一行自己的代码都没编到。因此：

- **加/改必填字段、改签名、改导出名，必须与所有构造点/调用点在**同一次编辑**里落地**——不要让工作区停留在编译不过的状态；
- **并行只在文件与层都真正不重叠时才开**：同一个 feature 目录（`features/auth`、`domain/auth` 之类）下的两条线应当串行；
- 交付顺序是"**先让门禁全绿再交接**"；多线并行时让**关键路径上那条线先提交**。

## 边界说明：改掉别人证据依赖的前提时，两边都要留话

实测两次：一处改动让另一个 ticket 的验收证据**早于**该改造；另一处把认证门收紧，
使另一个 ticket 某条验收的**复现路径**失效（机制证据仍有效，变的是可观察量）。

处理方式：在**改方**与**被影响方**两个 ticket 里各写一句——说明**变了什么**、**原证据还成立到哪一步**、**可观察量转移到哪个 ticket 去关**。
**不要悄悄改掉一个别人证据所依赖的前提。** 已验收不是"永不失效"，而是"失效时必须被记录"。
