# 并发与协作（多 agent 同仓时）

**构建产物与设备都是单例资源**：一个工作区只有一份 `entry/build`，一台设备同一时刻只允许一个操作者。
下面两把锁、以及围绕它们的窗口协议，都是从这一条推出来的。

## 开工前：先确认你在哪棵树

**开工前、以及每次构建/取证前，都用 `git rev-parse --show-toplevel` 确认自己在派单指定的那棵树。**

- 派单里**没有真路径**（占位符、空路径、或与 ticket 文件不一致）时，**不许自己挑树**——停下回报统筹者，不要以任何一方"为准"自行推进。
- 子 agent 的文件工具会把**相对路径**解析到会话工作区（= 主树），不是它被派的那棵树：
  `read`/`write`/`edit` 的 `file_path` **一律用绝对路径**（前缀 = 自己的树根），`pwsh` 一律带 `workdir`。
- **每写一批文件后自查**：`git -C <主树> status --porcelain` 必须为空，且自己的改动必须出现在 `git -C <自己的树> status` 里。

为什么这么严（两次实测事故）：一次是 agent 把**整个工期的改动、构建与取证**都做在了别人的 worktree 里，
两边 `entry/build` 与工作区互相污染，被污染方的产物无法证明"装的是哪一笔"、误置方那批帧与日志全部作废重做；
另一次是派单给了正确的绝对路径，但 agent 用相对路径调文件工具——**它以为自己在对的树里**，改动却落在主树。

## 两把锁与窗口协议

1. **构建锁**：每个 worktree 一把。任何 `hvigorw`（**含 `test`**）与 `devecocli build` 都会写 `entry/build` 与 `.hvigor` 缓存 ⇒ **同一时刻只允许一个构建进程**。
2. **设备锁**：每台模拟器或真机一把。`devecocli install/run`、`devecocli ui`（截图 / layout / 点击）、`devecocli log`、任何 `hdc` 命令 ⇒ 同一时刻只允许一个 agent 操作一台设备。

`devecocli run` 同时占两把锁（既构建又安装）。

**要独占时先向统筹者申请窗口**，不要在共享资源上自行重试或抢占。

为什么：两个并发构建会互相覆盖 `entry-default-signed.hap`，后者的产物会让前者**已装的 app 与源码对不上**；
两个 agent 操作同一台设备会让 install / 点击 / 截图互相踩踏。

## 干活期间：工作区是共享的

**任何"半成品"都会冻住别人的构建**（实测两次：一个 ticket 留下 21 个编译错误挡住另一个；
另一个给接口加了必填字段却没同步测试，对方 `COMPILE RESULT:FAIL {ERROR:2}`、一行自己的代码都没编到）。因此：

- **加/改必填字段、改签名、改导出名，必须与所有构造点/调用点在**同一次编辑**里落地**——不要让工作区停留在编译不过的状态。
- `git status` 或 `git log` 里出现**不属于你**的东西 ⇒ **立刻停下回报统筹者**：不要回退、不要提交、不要"顺手改成自己的"。

## 收尾：交接前

1. **门禁全绿**再交接——跑什么、怎么判见 `docs/agents/gates.md`。
2. 拿到窗口的 agent 明确回报**"窗口关闭"**。

## 边界：改掉别人证据依赖的前提时，两边都要留话

实测两次：一处改动让另一个 ticket 的验收证据**早于**该改造；另一处把认证门收紧，
使另一个 ticket 某条验收的**复现路径**失效（机制证据仍有效，变的是可观察量）。

- 在**改方**与**被影响方**两个 ticket 里各写一句——说明**变了什么**、**原证据还成立到哪一步**、**可观察量转移到哪个 ticket 去关**。
- **不要悄悄改掉一个别人证据所依赖的前提。** 已验收不是"永不失效"，而是"失效时必须被记录"。
